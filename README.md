# RevFlow - AI Revenue Automation Workbench

RevFlow is a portfolio-grade proof of concept for an AI-assisted order-to-cash revenue automation platform for modern B2B SaaS companies.

It mirrors the solution space behind platforms such as Zenskar, Stripe Billing, Chargebee, Metronome, Orb, Lago, and OpenMeter: flexible contract modeling, usage metering, deterministic billing, revenue recognition, auditability, and AI-assisted finance operations.

The goal is not to clone any single product. The goal is to build a credible end-to-end system that demonstrates full-stack product engineering depth in a complex finance domain.

## Product Thesis

Modern SaaS companies increasingly sell through custom contracts instead of simple flat subscriptions:

- Usage-based pricing
- Seat-based pricing
- Hybrid platform-fee plus usage pricing
- Tiered and volume pricing
- Minimum commitments
- Prepaid credits and rollover rules
- Free units and overages
- Custom payment terms
- Mid-term amendments
- Revenue recognition requirements
- Reporting needs such as MRR, ARR, revenue waterfall, and DSO

The hard problem is not just calculating a price. The hard problem is helping finance, sales, product, and engineering teams turn messy commercial agreements into correct, auditable, operational workflows without constant developer intervention.

RevFlow is designed around that problem: contract terms become the source of truth, usage is ingested and aggregated, invoices are generated from deterministic pricing logic, revenue recognition remains separate from billing, and AI helps with judgment-heavy workflows rather than replacing financial controls.

## Core User Journey

```txt
Contract terms
  -> AI extraction
  -> Human review and approval
  -> Billing configuration
  -> Usage ingestion
  -> Usage aggregation
  -> Draft invoice generation
  -> Invoice approval and issue
  -> Revenue schedule and journal entries
  -> Payment, reconciliation, and operational reporting
  -> Audit trail and exception review
```

## Domain Guardrails

These rules keep the POC credible as a finance system rather than a billing CRUD app.

- Contract terms are the source of truth for billing and revenue workflows.
- `Invoice` represents billing/cash timing; `RevenueSchedule` represents revenue recognition timing. They must stay separate.
- `UsageEvent` records are immutable and idempotent. Retries must not double-bill customers.
- `UsageAggregate` is a distinct, rerunnable step per contract, meter, and billing period. Invoices should not permanently depend on ad hoc raw-event scans.
- Pricing is deterministic code, not AI output. AI can extract proposed pricing config, but strategy code calculates money.
- Pricing rules are data/config driven so new models can be added without rewriting the invoice workflow.
- Approved contract terms should snapshot enough pricing context to explain future invoices even if catalog rules later change.
- Amendments should be append-only and effective-dated. Historical invoices and revenue schedules should not be rewritten.
- Finance-impacting changes must be auditable.
- Journal entries, tax, pricing math, and revenue recognition logic should never be generated by an LLM.

## Core Components

### Web App

Next.js dashboard for the finance/operator workflow:

- Customers and commercial account setup
- Catalog configuration
- Meter and pricing rule configuration
- Contract intake and approval
- Usage event visibility
- Invoice preview, detail, and approval
- Audit log inspection
- Revenue schedule review
- Operational job dashboard
- AI-assisted contract extraction and human review workspace

The frontend should feel like a real enterprise workflow tool, not a thin demo shell. It should prioritize dense but readable tables, forms, review states, validation feedback, calculation explainability, and clear state transitions.

### API Server

Express + TypeScript backend that owns domain behavior:

- Customer, catalog, contract, usage, invoice, and audit workflows
- Input validation with shared Zod schemas
- Business rules and financial state transitions
- Pricing calculations
- Usage ingestion and aggregation orchestration
- Invoice generation
- Revenue recognition scheduling
- Audit logging
- AI extraction orchestration

Routes stay thin. Services own business rules. Repositories own explicit SQL and mapping.

### Worker

Long-running Node process for asynchronous work:

- Usage aggregation
- Invoice generation jobs
- Revenue recognition scheduling
- Retryable failed jobs
- Future dunning, document generation, and integration jobs

Phase 2 keeps several workflows synchronous for demo reliability. Phase 3 starts moving the correct pieces behind queues and worker consumers.

### PostgreSQL

Source of truth for customers, contracts, catalog configuration, meters, usage events, usage aggregates, invoices, revenue schedules, journal entries, audit logs, and job runs.

This domain is relational by nature: foreign keys, period boundaries, state transitions, and explainable joins matter.

### Redis + BullMQ

Queue infrastructure for buffering work, absorbing usage spikes, retrying failed jobs, and decoupling user-facing API latency from background processing.

### AI Layer

AI is reserved for judgment-heavy or unstructured-input workflows.

Phase 5 implements:

- Pasted contract-text extraction into draft terms
- Confidence, ambiguity, missing-field, and source-evidence visibility
- Provider-neutral mock and local Ollama inference

Future candidates include invoice anomaly detection, natural-language finance Q&A, and drafting dunning or collections communications with human review.

AI does not directly activate billing. It produces drafts, explanations, or recommendations that must be reviewed or governed by deterministic rules.

## Key Workflows

### 1. Contract Intake And AI Extraction

User pastes contract text. The selected provider can extract:

- Customer name and billing email
- Contract start and end dates
- Billing frequency and payment terms
- Product or plan name
- Pricing model, unit price, and currency
- Revenue recognition method
- Ambiguities, missing fields, confidence, and source snippets

Output is persisted as a reviewable draft, not active billing configuration.

### 2. Human Review And Approval

Finance user reviews the extraction:

- Accept, edit, or reject every extracted field
- Resolve ambiguous or missing terms
- Approve or reject the reviewed extraction
- Apply an approved extraction to a matched/created customer and draft contract
- Add trusted catalog/price-rule configuration manually
- Approve the resulting contract through the existing activation workflow

Review and apply actions write to the audit log. Applying AI output never approves or activates the contract.

### 3. Product Catalog And Pricing Configuration

RevFlow separates reusable catalog configuration from customer-specific contracts:

- Products define what is sold
- Meters define what is measured
- Plans define reusable commercial packages
- Price rules define calculation behavior
- Contracts can override plan defaults for enterprise deals

Supported or planned pricing models:

- Flat recurring fee
- Per-seat pricing
- Pay-as-you-go usage
- Tiered pricing
- Volume pricing
- Included units plus overage
- Minimum commitment
- Prepaid credit burn-down
- Hybrid subscription plus usage
- Ramp-up pricing and proration in later phases

### 4. Usage Metering

```txt
POST /usage/events
  -> validate event
  -> dedupe by idempotency key
  -> store immutable raw event
  -> enqueue or run aggregation
  -> aggregate by contract, meter, and period
  -> expose aggregate for invoice generation and reporting
```

Important concerns:

- Idempotency
- Backpressure
- Late-arriving events
- Period boundaries
- Aggregation correctness
- Query performance
- Re-runnable backfills and corrections

### 5. Invoice Lifecycle

Invoices are generated as drafts first.

```txt
draft -> approved -> issued -> paid
      -> void
      -> credited
```

Draft invoices can be inspected before issue:

- Source contract
- Billing period
- Usage totals
- Pricing rule applied
- Line item calculations
- Manual adjustments
- Taxes placeholder
- Revenue recognition impact

### 6. Revenue Recognition

RevFlow implements ASC 606-lite behavior for portfolio and interview purposes.

Recognition concepts:

- Performance obligations
- Transaction price allocation
- Deferred revenue
- Unbilled revenue
- Revenue waterfall
- Journal entries

Recognition methods:

- Immediate recognition
- Straight-line over service period
- Usage-based recognition
- Milestone-based recognition

### 7. Payment, Collections, And Reporting

Later phases can simulate the downstream order-to-cash workflow:

- Payment receipt
- Reconciliation against invoices
- Dunning reminders for overdue invoices
- AR status
- MRR, ARR, NRR, revenue waterfall, and DSO dashboards
- ERP/GL export stubs

### 8. Audit And Operations

Finance systems must be explainable.

Audit logs track:

- Customer, catalog, and contract changes
- AI extraction review and approval
- Pricing rule edits
- Usage ingestion
- Invoice generation and approval
- Invoice state transitions
- Revenue schedule generation

Operational views track:

- Failed usage events
- Queue jobs
- Invoice generation runs
- Revrec scheduler runs
- AI extraction runs

## Pricing Engine Design

The pricing engine should be deterministic, testable, and isolated from HTTP and database concerns.

```ts
interface PricingStrategy<TConfig, TUsage> {
  calculate(input: {
    config: TConfig;
    usage: TUsage;
    period: BillingPeriod;
    contractContext: ContractContext;
  }): PriceResult;
}
```

Each pricing model is implemented as a separate strategy:

- `FlatRateStrategy`
- `SeatBasedStrategy`
- `UsageBasedStrategy`
- `TieredUsageStrategy`
- `VolumePricingStrategy`
- `MinimumCommitmentStrategy`
- `CreditBurndownStrategy`
- `HybridPricingStrategy`

The engine returns calculation snapshots that can be stored on invoice line items for explainability.

## Current Implementation Status

Phases 1 through 5 are implemented as a working product slice.

Completed:

- Monorepo scaffold with apps and shared packages
- Express API and Next.js dashboard
- Postgres migrations and migration runner
- Docker Compose for Postgres and Redis
- Customers module
- Catalog module for products, meters, plans, and price rules
- Contract draft, line item, and approval workflow
- Usage ingestion with idempotency
- Persisted usage aggregates with rerunnable upserts
- Worker-backed usage aggregation path through BullMQ
- Draft invoice generation from approved contracts and usage aggregates
- Pricing engine with flat, per-unit, and tiered strategies
- Invoice detail and approval
- Audit event writes plus audit API/page
- Ops job-run API/page for background work
- Seed data script for local demos
- Focused pricing and invoice calculation tests
- ASC 606-lite revenue recognition schedules
- Journal entry generation from revenue schedules
- Revenue recognition API and `/revenue` UI
- Persisted AI extraction runs with provider, model, prompt, confidence, ambiguity, and error metadata
- Provider-neutral AI boundary with deterministic mock and opt-in local Ollama adapters
- `/ai` contract extraction and field-level human review workspace
- Approved extraction application to matched/created customers and draft contracts only
- Audit visibility for AI extraction creation, review, failure, and apply actions

Known remaining shortcuts:

- Invoice generation is still synchronous in the API.
- Invoice generation retains raw-event fallback if a usage aggregate is missing.
- Contract approval does not yet snapshot all pricing config needed for long-term historical explainability.
- Job-run visibility is intentionally simple and focused on recent background jobs.
- Revenue schedule and journal-entry generation are synchronous for POC clarity.
- Usage-priced invoice lines currently default to immediate recognition; full usage-based recognition remains a later hardening path.
- AI intake is paste-based text; PDF upload, OCR, and multi-document reconciliation are deferred.
- Applying reviewed AI output creates a draft contract without trusted catalog or price-rule links.
- Local small-model confidence may be optimistic, so explicit field decisions and contract approval remain mandatory.

These shortcuts are acceptable for the current POC and become inputs to Phase 6 and the production-hardening notes.
